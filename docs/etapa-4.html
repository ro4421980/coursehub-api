1. Resumen ejecutivo

Se implementó y consolidó una suite unitaria para la regla de negocio más sensible de courses: quién puede actualizar un curso. La suite demuestra con un repositorio simulado que:

  • un docente propietario puede actualizar;
  • un docente ajeno no puede;
  • un estudiante nunca puede, aunque su id coincida con el propietario;
  • un administrador puede actualizar cualquier curso;
  • un curso inexistente produce un error de recurso no encontrado;
  • una actualización parcial conserva los campos no enviados;
  • el id y el propietario no se pueden cambiar desde el cuerpo de la petición.

Además, el controlador se prueba como adaptador puro: se verifica que delega el id de la ruta, el DTO y la identidad autenticada (request.user) al caso de uso, y que no acepta identidad ni propiedad enviadas por el cliente.

3. La regla que se protege

UpdateCourseUseCase concentra la decisión de negocio. El controlador no decide autorización: solo traduce HTTP al caso de uso.

const isAdmin = input.actor.role === UserRole.ADMIN;
const isOwner = course.createdByUserId === input.actor.id;
const isTeacher = input.actor.role === UserRole.TEACHER;

if (!isAdmin && !(isTeacher && isOwner)) {
  throw new CourseAccessDeniedError();
}

Matriz de decisión:

Rol del actor ¿Es propietario? ¿Puede actualizar? Resultado esperado
admin Sí Sí Actualiza y persiste
admin No Sí Actualiza y persiste
teacher Sí Sí Actualiza y persiste
teacher No No CourseAccessDeniedError; no guarda
student Sí No CourseAccessDeniedError; no guarda
Cualquiera Curso inexistente No CourseNotFoundError; no guarda

La regla también protege la integridad del recurso: después de autorizar, solo se copian title y level. id y createdByUserId son datos de identidad y no pueden modificarse con un PATCH, aunque un llamador omita la validación del DTO.

4. Diseño de las pruebas del caso de uso

4.1 Repositorio simulado

InMemoryCourseRepository implementa el puerto real CourseRepository con un arreglo en memoria:

  • no importa TypeORM, pg ni Nest;
  • implementa findById, save, create, delete y findPage;
  • cada prueba crea una instancia nueva con un curso fijo;
  • save falla si se intenta guardar un curso que no existe, lo que evita falsos positivos;
  • vi.spyOn(repository, 'save') permite comprobar que una operación rechazada no escribió.

Se eligió un fake en memoria, y no un mock de todas las funciones, porque permite verificar el efecto real de la regla: el estado del repositorio después de la operación. El espía se usa solo para la garantía negativa (“no se llamó a save”).

4.2 Casos y comportamiento protegido

# Prueba Escenario Decisión verificada
1 updates and persists the course when the teacher owns it Docente propietario actualiza título y nivel Éxito, save una vez y estado persistido
2 keeps fields that the partial update does not mention Docente envía solo title Actualización parcial sin borrar level
3 rejects a teacher who does not own the course Docente ajeno intenta actualizar CourseAccessDeniedError, sin escritura y estado intacto
4 rejects a student even when the student id matches the owner Estudiante con el mismo id del propietario El rol se evalúa además de la propiedad
5 allows an admin to update a course owned by someone else Administrador sobre curso ajeno Excepción legítima de la regla
6 reports a missing course before applying the authorization rule Id 999 CourseNotFoundError con el id correcto, sin escritura
7 cannot change the id or the owner through the update payload Cuerpo hostil con id y createdByUserId La integridad del recurso prevalece

Las pruebas 3, 4 y 7 son las que convierten la suite en una red de seguridad de negocio, no en una simple ejecución de líneas.

5. Prueba del controlador

El controlador se instancia directamente con casos de uso simulados. No se levanta un servidor HTTP, no se abre un puerto y no se usa supertest.

# Prueba Qué verifica
1 delegates the parsed route id to GetCourseUseCase El id de la ruta llega como número al caso de uso
2 delegates the list query without rewriting it El DTO de consulta se delega sin transformaciones ocultas
3 updates with the route id, the DTO and the authenticated actor courseId, changes y actor llegan exactamente al caso de uso
4 does not let the body override identity or ownership on PATCH id, createdByUserId y role del cuerpo se descartan; manda request.user
5 creates the course with the authenticated creator, not with body data El propietario se toma de la identidad autenticada
6 delegates DELETE to the use case with the route id El id de la ruta se delega en el caso de uso de borrado

La prueba 4 es la evidencia explícita de delegación de identidad: aunque el cuerpo incluya role: admin o createdByUserId: 999, el controlador envía el usuario autenticado y solo los campos permitidos del DTO. Para lograrlo de forma defensa en profundidad, el controlador usa pickCourseChanges(), que copia únicamente title y level cuando están presentes.

6. Frontera entre prueba unitaria e integración

La Semana 12 exige pruebas sin PostgreSQL ni red. Para que esa afirmación sea verificable, la suite unitaria se separó de las pruebas HTTP:

Tipo Ubicación Comando Usa red/DB
Unitaria src/**/*.spec.ts npm test No
Integración HTTP test/*.e2e-spec.ts npm run test:e2e Red local en proceso; app.e2e-spec.ts puede requerir PostgreSQL

Cambios realizados para mantener la frontera:

  1. Las pruebas HTTP de CoursesController que estaban en src/courses/courses.controller.spec.ts se conservaron en test/courses.e2e-spec.ts.
  2. Las pruebas HTTP de AuthController se movieron a test/auth.e2e-spec.ts.
  3. El nuevo src/courses/courses.controller.spec.ts es unitario puro.
  4. La suite unitaria ya no importa supertest ni arranca una aplicación Nest con servidor.

No se perdió cobertura: las 28 pruebas HTTP movidas siguen pasando con vitest --config vitest.config.e2e.ts. Simplemente ya no cuentan como evidencia unitaria de la Semana 12.

8. Demostración: cambiar la regla y ver fallar la prueba

La demo está automatizada en docs/etapa-4-demo.mjs y se ejecuta con:

npm run demo:etapa4

El script hace cinco pasos y restaura el archivo en un bloque finally:

  1. ejecuta la suite completa en verde;
  2. debilita temporalmente la regla de propiedad;
  3. ejecuta el spec del caso de uso y exige que falle;
  4. restaura el archivo original;
  5. vuelve a ejecutar la suite completa y exige que pase.

8.1 Mutación aplicada

- if (!isAdmin && !(isTeacher && isOwner)) {
+ if (!isAdmin && !isTeacher) { // MUTACION TEMPORAL

La mutación elimina isOwner: cualquier docente pasa la autorización, sin importar quién creó el curso.

8.4 ¿Qué quedaría desprotegido si se borrara esa prueba?

Si se elimina rejects a teacher who does not own the course, la mutación anterior pasaría inadvertida: las otras 6 pruebas del caso de uso seguirían en verde. En concreto, quedarían sin red de seguridad:

  • Escalada horizontal de privilegios: un docente podría editar cursos de otros docentes. El RolesGuard solo comprueba que el rol sea teacher; la decisión de propiedad vive en el caso de uso.
  • Integridad de los cursos ajenos: títulos y niveles podrían alterarse sin ser el propietario, con impacto directo en el catálogo.
  • Trazabilidad: el curso conservaría createdByUserId del propietario original, pero con contenido modificado por otra persona; la auditoría quedaría engañosa.
  • Regresión silenciosa: un refactor que sustituya !(isTeacher && isOwner) por !isTeacher, o que elimine isOwner, no sería detectado por las demás pruebas.

La prueba no verifica “que se ejecute una línea”: verifica que no se escriba en el repositorio y que el estado permanezca intacto cuando la identidad no autoriza. Esa es la diferencia entre cobertura y protección.

12. Limitaciones y siguiente etapa

  • La suite unitaria no prueba transacciones, concurrencia, restricciones de PostgreSQL ni migraciones. Eso corresponde a la integración de la Semana 13.
  • test/app.e2e-spec.ts arranca AppModule completo y puede necesitar la base de datos local; por eso no forma parte de npm test.
  • La cobertura global incluye módulos antiguos con menor cobertura. La métrica relevante de esta entrega es la cobertura y, sobre todo, la detección de mutaciones en la regla protegida.
  • El script de demo restaura el archivo en finally; no se debe interrumpir con Ctrl+C mientras la mutación está activa. Si ocurriera, basta con ejecutar git checkout -- src/courses/application/use-cases/update-course.use-case.ts.
  • No se inventaron reglas nuevas (por ejemplo, rechazar un PATCH vacío): la suite protege el comportamiento definido en la Etapa 3.
